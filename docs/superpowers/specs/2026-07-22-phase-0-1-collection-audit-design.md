# Phase 0.1 Collection Audit — Design

## Objective

Stabiliser le générateur d'inventaire de la collection sans supprimer le WIP
hérité, restaurer la compatibilité des 73 tests du HEAD `f500166`, puis rendre
les artefacts, rapports et gates suffisamment fiables pour servir de fondation
à la Phase 1. La Phase 0.1 se termine avec `--validate-model` vert,
`--fail-on-new` vert contre une baseline stabilisée et `--release-strict` rouge
pour une liste explicite et déterministe de dettes de publication.

## Constraints

- Aucun reset, restore, stash, clean, rebase, merge, switch ou push forcé.
- Les deux fichiers WIP initiaux sont conservés et corrigés, jamais remplacés en
  bloc par leur version HEAD.
- Aucun ajout fonctionnel postérieur ne commence avant 73/73 tests historiques.
- Chaque comportement nouveau suit un cycle test rouge, correctif minimal, test
  vert, puis vérification de non-régression.
- Les contrats publics restent dans les modules existants jusqu'à stabilisation ;
  aucune extraction multi-modules prématurée.
- La baseline définitive ne peut être créée qu'après stabilisation de la
  classification, des renderers, des compteurs, des fingerprints et du modèle.

## Mandatory Recovery Preflight

Avant le premier changement dans `scripts/inventory_collection.py` ou
`scripts/inventory_graph.py`, les preuves suivantes doivent exister et être
vérifiées :

1. `audit/PHASE_0_1_REPRISE_WIP.md` énumère les 36 tests cassés, les regroupe par
   propagation de cause et identifie les modifications responsables ;
2. une revue Chutes indépendante est enregistrée sous `audit/chutes/` ;
3. les recommandations Chutes retenues ou rejetées sont confrontées à des
   commandes locales et la décision est justifiée ;
4. `git diff --check` est propre ;
5. le premier cycle TDD cible le fallback de classification, plus petit
   correctif susceptible de restaurer le maximum de tests.

Ce préflight est un gate bloquant de reprise, pas une tâche à reconstituer après
le correctif.

## Chosen Approach

Le WIP est repris par incréments. Le premier incrément rétablit le fallback de
classification sans exiger les nouveaux fichiers de configuration, révèle les
régressions masquées, puis restaure 73/73. Les incréments suivants stabilisent
successivement les formats machine, les rapports et gates, la qualification de
dette, la transaction de génération, les builds observés et enfin la CI.

Une réécriture parallèle est exclue car elle dupliquerait l'analyse existante.
Une extraction en nouveaux modules de production est reportée car elle
modifierait les contrats au moment où ils doivent d'abord être figés.

## Architecture

### Canonical inventory

`build_inventory()` reste la source de vérité dérivée des fichiers suivis par
Git. Son champ `anomalies` contient uniquement les anomalies brutes produites par
l'analyse. Ces objets ne sont ni supprimés, ni réécrits, ni enrichis en place par
les dispositions ou la baseline.

Les champs de premier niveau distinguent :

- `declared_assemblies` : assemblages déduits des déclarations et sources ;
- `observed_builds` : builds attestés par un manifeste produit pendant une
  exécution réelle ;
- `assemblies` : alias de compatibilité temporaire vers les assemblages déclarés
  tant que les tests et consommateurs historiques l'exigent.

Une analyse AST ou par expression régulière peut renseigner un assemblage
déclaré, jamais prouver seule le contenu final d'un PDF.

### Source classification

`audit/SOURCE_ROLES.yaml` est une configuration versionnée et validée. Un
fallback canonique en code préserve la compatibilité lorsque le fichier est
absent dans une fixture ou un consommateur externe.

L'ordre va du plus spécifique au plus général : exclusions, fixtures,
`harvest_candidate`, références visuelles, archives, dépendances générées,
validations, production, transversal. Il garantit notamment que :

- `_harvest/**/*.candidate.tex` n'est jamais un objet de production ;
- `Mathematiques/manuel-maths/build/maquette-v5/renvois.tex` est une dépendance
  générée ;
- les répétitions intentionnelles de maquette peuvent recevoir une disposition
  sans disparaître des anomalies brutes.

### Machine artifacts and schemas

Les schémas JSON Schema versionnés résident dans `audit/schemas/v1/` :

- `inventory-collection.schema.json` ;
- `ecarts-et-contradictions.schema.json` ;
- `matrice-livrables.schema.json` ;
- `source-roles.schema.json` ;
- `anomaly-dispositions.schema.json` ;
- `anomalies-baseline.schema.json` ;
- `build-manifest.schema.json`.

Chaque YAML est parsé par `yaml.safe_load`, chaque JSON par `json.loads`, puis le
payload chargé est validé par le schéma déclaré. Le commentaire HTML
`<!-- AUTO-GÉNÉRÉ ... -->` est remplacé par le commentaire YAML valide
`# generated by ...`. L'absence d'un schéma requis ou une version inconnue est
une erreur de modèle.

Les artefacts machine sont répartis en trois contrats explicites :

1. sorties du modèle : `audit/INVENTAIRE_COLLECTION.json`,
   `audit/ECARTS_ET_CONTRADICTIONS.yaml` et
   `audit/MATRICE_LIVRABLES.yaml` ;
2. contrôles versionnés : `audit/SOURCE_ROLES.yaml` et
   `audit/ANOMALY_DISPOSITIONS.yaml` ;
3. états référencés : `audit/ANOMALIES_BASELINE.json` et
   `audit/BUILD_MANIFEST.json`.

Les trois sorties du modèle partagent exactement `schema_version`,
`source_digest`, `model_digest` et la même structure de provenance.
`source_digest` est le SHA-256 d'une séquence triée de couples
`(chemin_relatif_utf8, octets_du_fichier)` pour toutes les sources classifiées
participant au modèle, en excluant les sorties générées, la baseline et les
manifestes afin d'éviter les cycles.

`canonical_model_payload` est l'unique payload commun hashé : il contient
`source_digest`, `source_files`, `manuals`, les anomalies brutes,
`reference_graph`, `correction_links`, `declared_assemblies`, `pdfs`,
`report_reconciliation`, `coherence_checks` et `deliverable_matrix`. Il exclut
entièrement l'enveloppe d'artefact, la provenance, `observed_builds`,
`model_digest` et tout autre champ digest. `model_digest` est le SHA-256 de ce
payload sérialisé en JSON UTF-8 sans indentation, clés triées, séparateurs
`,`/`:`, tableaux conservés dans leur ordre sémantique. Les trois sorties
injectent ensuite ce hash déjà calculé ; elles ne se hashent jamais elles-mêmes.
L'état des builds possède un `build_state_digest` séparé.

Les contrôles possèdent leur propre `control_digest`, calculé sur leur payload
canonique sans le champ digest. La baseline référence les `source_digest` et
`model_digest` qu'elle fige ; chaque build observé référence les mêmes digests.
`--validate-model` vérifie ces égalités croisées sur tous les artefacts, ce qui
constitue la cohérence globale sans introduire de digest auto-référentiel.

### Human reports

`ETAT_COLLECTION.md` devient un tableau de bord court : digest, provenance
synthétique, objets réels par manuel, état des gates, nombre de bloqueurs et
liens vers les artefacts machine. Les listes exhaustives restent dans JSON/YAML.

`INVENTAIRE_COLLECTION.md` et `AUDIT_CONSOLIDE.md` affichent les champs réellement
présents pour chaque anomalie. Aucun fallback `id=—, detail=—, code=—` n'est
autorisé. Le nombre d'objets est `len(chapter["objects"])` agrégé, jamais la somme
de métriques susceptibles de compter plusieurs dimensions du même objet.

### Gate model

Chaque gate produit une structure avec nom, succès, code de sortie, dimensions
couvertes et raisons triées :

- `--check` compare le rendu en mémoire aux fichiers suivis sans écrire ;
- `--validate-model` valide parsing, schémas, digests et cohérences internes ;
- `--release-strict` exige l'absence de dette incompatible avec la publication ;
- `--fail-on-new` compare la dette à la baseline stabilisée ;
- `--require-clean` refuse les modifications suivies et les fichiers non suivis
  pertinents.

Les dimensions exposées sont `structure`, `pedagogy`, `regulation`,
`mathematics`, `execution`, `visual` et `print`. Une dimension non vérifiée reste
explicitement `not_covered`, jamais implicitement verte.

La baseline n'affecte pas `--release-strict`. Une dette historique inchangée
peut passer `--fail-on-new` tout en restant un bloqueur de publication.

`missing_corrections` appartient toujours aux anomalies structurelles
bloquantes. Pour chaque manuel :

- `phase0_structural_eligible` vaut vrai uniquement si aucune anomalie
  structurelle active ne le concerne et si ses déclarations minimales sont
  cohérentes ; il n'exige pas que les dimensions hors Phase 0 soient couvertes ;
- `publication_eligible` vaut vrai uniquement si
  `phase0_structural_eligible` est vrai, si toutes les variantes requises ont un
  build observé valide et si les sept dimensions sont `passed` ;
- une disposition non bloquante peut modifier l'évaluation d'un gate, jamais la
  liste des anomalies brutes ; une `accepted_exception` expirée est bloquante.

Les codes de sortie sont stables : `0` succès, `2` usage CLI, `3` dérive
`--check`, `4` dépôt non propre, `5` dette nouvelle/baseline non exploitable,
`6` modèle invalide, `7` publication refusée et `8` précondition de mise à jour
de baseline. Si plusieurs actions sont combinées, l'ordre d'évaluation est
propreté, validation, check, dette, publication ; le premier échec détermine le
code.

### Raw anomalies, dispositions and baseline

Les trois couches utilisent des fichiers ou structures séparés :

1. les anomalies brutes immuables dans l'inventaire ;
2. `audit/ANOMALY_DISPOSITIONS.yaml`, qualification humaine versionnée ;
3. `audit/ANOMALIES_BASELINE.json`, registre actif/résolu de comparaison.

Une disposition autorisée vaut `open_debt`, `false_positive`,
`generated_dependency`, `intentional_reuse`, `accepted_exception` ou `fixed`.
Elle référence un fingerprint, mais ne modifie pas l'anomalie. Une
`accepted_exception` exige portée, justification, auteur, preuve, décision
humaine, caractère bloquant et expiration ou condition de réexamen. Une
exception expirée redevient active.

Tous les enregistrements de disposition exigent `fingerprint`, `disposition`,
`owner`, `justification`, `approved_by` et `decision_ref`. Les dispositions
`false_positive`, `generated_dependency`, `intentional_reuse` et `fixed`
exigent aussi une `proof`. `accepted_exception` exige en plus `scope`,
`author`, `blocking`, `expires_at` ou `review_condition`. `open_debt` exige un
propriétaire et une qualification, mais pas une preuve de correction.

La baseline contient `provisional`, la version de schéma, la version de
fingerprint, le SHA Git, son empreinte précédente, les anomalies actives, les
fingerprints résolus et l'historique des mises à jour. Une baseline provisoire ne
peut jamais rendre `--fail-on-new` obligatoire ou vert.

### Fingerprints and comparison

`fingerprint_schema_version` commence à 1. Le hash porte sur un tuple canonique :
catégorie, manuel, chapitre, source relative normalisée, champ, cible ou ID et
code de raison stable. Il exclut texte libre complet, dates, chemins absolus,
numéros de lignes, ordre de listes, compteurs agrégés et messages d'outils.

La comparaison est une fonction pure sur un multiensemble de fingerprints
individuels, pas un total par catégorie. Elle distingue `new`, `unchanged`,
`resolved`, `modified` et `regression`, mais ne modifie aucun fichier ni registre.
Elle émet un projet de transition ; seul `--update-baseline` l'applique.

Un `locator_key` séparé du fingerprint — catégorie, manuel, chapitre, source,
champ et cible/ID — rapproche une ancienne et une nouvelle version du même cas.
Même `locator_key` avec fingerprint différent vaut `modified`; une ancienne clé
absente vaut `resolved`; une nouvelle clé sans correspondance vaut `new`. Un
total stable avec remplacement d'une anomalie échoue donc. L'ordre de sévérité
est `info < warning < blocking < regression`; une hausse échoue même si le
fingerprint ne change pas. Disposition et sévérité sont comparées comme
métadonnées de baseline, sans entrer dans le fingerprint.

Une disparition n'échoue pas : le rapport la classe amélioration et le projet de
transition propose son ajout au registre résolu. La réapparition d'un fingerprint
déjà présent dans ce registre est une régression.

`--fail-on-new` échoue aussi sur augmentation d'occurrences, aggravation de
sévérité, perte d'une disposition approuvée, modification substantielle et
champs de qualification obligatoires manquants.

Toute future évolution de l'algorithme de fingerprint exige migration, rapport
avant/après, tests et commit dédié.

### Baseline update

La baseline n'est jamais mise à jour par la CI. La seule écriture passe par :

```bash
python scripts/inventory_collection.py --update-baseline \
  --reason "..." --approved-by "..."
```

La commande exige un dépôt propre, un modèle valide, une justification non vide
et un approbateur. Elle affiche et enregistre le diff, le SHA Git, les anciennes
et nouvelles empreintes, conserve le registre résolu et produit un rapport de
mise à jour. Elle refuse une baseline définitive tant que les préconditions de
stabilisation listées dans cette spécification ne sont pas satisfaites.

Ce refus est implémenté par un gate structuré `baseline_ready`, composé de dix
checks triés :

1. suite historique et tests Phase 0.1 exécutés avec succès ;
2. parsing et schémas de tous les artefacts verts ;
3. renderers sans placeholder interdit et état synthétique borné ;
4. cohérence des compteurs d'objets ;
5. tous les `_harvest/**/*.candidate.tex` classés `harvest_candidate` ;
6. `build/maquette-v5/renvois.tex` classé `generated_dependency` ;
7. chaque répétition de maquette acceptée possède une disposition
   `intentional_reuse`, une preuve et une décision humaine ;
8. chaque faux positif possède une disposition `false_positive` justifiée et
   chaque anomalie active possède propriétaire/qualification obligatoires ;
9. version de fingerprint supportée et recalcul de tous les fingerprints
   déterministe ;
10. `--validate-model` vert sur les digests et cohérences finales.

Les checks automatiques sont recalculés par la commande. Les décisions humaines
sont attestées dans `ANOMALY_DISPOSITIONS.yaml`; une simple valeur booléenne de
readiness ne suffit pas.

### Provenance and transactional writes

La provenance commune contient SHA Git, branche, état propre/sale, fichiers
modifiés, fichiers non suivis pertinents, version et SHA-256 du générateur et
versions réelles des outils. Les valeurs nécessaires à la reproductibilité sont
issues de Git ou de `SOURCE_DATE_EPOCH`, jamais de l'heure murale non contrôlée.

Les chemins de sortie sont résolus sous la racine, y compris les symlinks. Le
verrou couvre rendu, comparaison et remplacement du lot complet. Les nouveaux
fichiers sont préparés et validés avant le premier remplacement ; les anciens
octets sont restaurés si une opération échoue. Le verrou porte une identité de
processus et une politique testée pour les verrous obsolètes.

### Observed build manifest

`audit/BUILD_MANIFEST.json` contient une enveloppe et une liste de builds
réellement observés. Le manifeste n'est jamais créé par l'inventaire statique :
il est émis par la commande de build réelle. Le master généré encadre chaque
objet avec des marqueurs `NEXUS_OBJECT_BEGIN/END` écrits dans le log TeX ; le
moteur est lancé avec `-recorder`, puis la commande croise l'ordre des marqueurs
du `.log` avec les entrées réellement ouvertes du `.fls`. Une intention
d'assemblage absente de ces deux traces n'est pas comptée comme traitée. Après le
succès du processus LaTeX, la commande calcule le SHA-256 du PDF produit,
interroge `pdfinfo` pour les pages, capture les versions effectives des outils et
joint les résultats des gates exécutés sur les mêmes digests. Cette preuve
atteste les entrées effectivement traitées, sans prétendre prouver à elle seule
leur rendu visuel ou leur présence sur une page donnée.

Chaque entrée exige SHA Git, digest source et modèle, trace ordonnée des objets,
variante, chemin PDF, nombre de pages, SHA-256, versions des outils et résultats
des gates. L'importeur valide le manifeste, recalcule SHA/pages depuis le PDF et
rejette tout écart. `build_inventory()` reste la vérité statique ;
`observed_builds` est une vue séparée importée depuis ces preuves d'exécution
validées. Le manifeste est exclu de `source_digest` pour éviter un cycle. Une
liste vide est valide pour le modèle mais reste bloquante pour la publication.

### CI

`.github/workflows/ci-audit-collection.yml` exécute Ruff, mypy, tests, couverture
lignes et branches, validation de tous les JSON/YAML, deux générations dans des
répertoires isolés avec comparaison byte à byte, `--check`,
`--validate-model`, `--fail-on-new`, puis un test contrôlé confirmant que
`--release-strict` échoue avec son code et ses bloqueurs attendus. La CI n'appelle
jamais `--update-baseline` et publie les rapports générés comme artefacts.

## Error Handling

Les erreurs de parsing, schéma, digest, chemin, verrou, baseline et manifeste
deviennent des raisons structurées et des codes de sortie documentés. Aucune
erreur de configuration obligatoire n'est silencieusement convertie en `{}`. Le
fallback n'est permis que lorsque l'absence est explicitement compatible, comme
pour les rôles dans les fixtures historiques.

Une génération qui échoue avant validation ou pendant l'application laisse tous
les fichiers précédents byte à byte identiques.

## Testing Strategy

Le premier jalon ajoute un test ciblé du fallback, observe son échec, applique le
correctif minimal et relance les 73 tests. Chaque défaut masqué reçoit ensuite un
test ciblé avant correction.

Les jalons suivants ajoutent des tests unitaires des schémas, renderers, gates,
classifications, fingerprints, comparaisons, chemins, verrous, rollback et
manifestes. Les tests d'intégration exécutent la CLI dans des dépôts Git
temporaires. La dernière vérification couvre lint, typage, couverture lignes et
branches, parsing de tous les artefacts, reproductibilité et codes de sortie.

## Commit Boundaries

Les commits suivent l'ordre fonctionnel approuvé, avec un commit de gel technique
supplémentaire imposé par la précondition de dépôt propre :

1. `[AUDIT][P0.1] restaure les tests historiques du WIP`
2. `[AUDIT][P0.1] stabilise formats et schemas`
3. `[AUDIT][P0.1] fiabilise les rapports et compteurs`
4. `[AUDIT][P0.2] ajoute classification et dispositions`
5. `[AUDIT][P0.2] ajoute baseline et comparaison de dette`
6. `[AUDIT][P0.2] ajoute provenance et ecritures transactionnelles`
7. `[AUDIT][P0.2] distingue assemblages declares et builds observes`
8. `[AUDIT][P0.2] fige la baseline initiale stabilisee`
9. `[CI][AUDIT] branche les gates de Phase 0.1`

Le commit de gel supplémentaire est nécessaire pour respecter simultanément la
précondition « dépôt propre » de `--update-baseline` et l'interdiction de
réécrire l'historique : l'implémentation doit être commitée avant que la commande
puisse produire la baseline définitive. Les huit intitulés fonctionnels demandés
restent dans leur ordre ; le gel explicite est inséré avant la CI.

Avant chaque commit : tests ciblés, tests de jalon, `git diff --check` et
`git status --short`. La branche n'est poussée et la draft PR n'est ouverte
qu'après la vérification Phase 0.1 complète.
