\section*{Situation pratique P5 --- corriger une fonction récursive et la tester}

\subsection*{Document fourni}

Le fichier \lstinline{chiffres.py} contient une fonction \textbf{fautive} et le
jeu de tests qui servira à l'évaluation.

\begin{python}
def somme_chiffres(n):
    if n == 0:
        return 0
    return n % 10 + somme_chiffres(n % 10)
\end{python}

\subsection*{Travail demandé}

\begin{enumerate}
  \item Exécuter \lstinline{somme_chiffres(7)}. Décrire précisément ce qui se
    passe, et pourquoi.

  \item Corriger la fonction. Une seule opération est en cause : dire laquelle,
    et par quoi la remplacer.

  \item Écrire la spécification en docstring : une précondition et trois
    postconditions, dont l'une relie la somme des chiffres à $n$ modulo $9$.
    Rendre la précondition exécutable.

  \item Exécuter le jeu de tests fourni. Il doit passer entièrement, y compris
    la vérification de la postcondition modulo $9$ sur cinq cents entiers.

  \item Vérifier que les appels \lstinline{somme_chiffres(-1)},
    \lstinline{somme_chiffres(3.5)} et \lstinline{somme_chiffres("12")} sont
    tous les trois refusés.
\end{enumerate}

\subsection*{Réponses attendues}

\textbf{Question 1.} L'appel provoque une \lstinline{RecursionError}. Pour
$n = 7$, l'expression \lstinline{n % 10} vaut encore $7$ : la fonction
s'appelle avec le \textbf{même} argument, indéfiniment. Le cas d'arrêt
\lstinline{n == 0} n'est jamais atteint.

\medskip
\textbf{Question 2.} L'appel récursif doit porter sur \lstinline{n // 10}, qui
retire le dernier chiffre, et non sur \lstinline{n % 10}, qui l'isole. Le cas
d'arrêt devient \lstinline{n < 10}.

\medskip
\textbf{Question 3.} Précondition : $n$ est un entier positif ou nul.
Postconditions : le résultat est un entier positif ou nul ; il est nul si et
seulement si $n$ l'est ; il est congru à $n$ modulo $9$.

\subsection*{Critique}

\begin{itemize}
  \item \textbf{Corriger le cas d'arrêt au lieu de l'appel.} Écrire
    \lstinline{if n < 10} sans changer \lstinline{n % 10} en
    \lstinline{n // 10} fait renvoyer $n \bmod 10$ à tout coup : la fonction ne
    plante plus, et elle est fausse. C'est pire qu'avant.
  \item \textbf{La postcondition modulo $9$.} Elle n'est pas décorative : c'est
    la seule qui teste le résultat sur cinq cents valeurs sans avoir à les
    calculer une par une.
  \item \textbf{Accepter les flottants.} \lstinline{3.5 % 10} vaut $3{,}5$ et ne
    lève aucune erreur : sans contrôle de type, la fonction renvoie un flottant
    absurde.
\end{itemize}

\subsection*{Portée pédagogique}

La situation part d'un code qui \emph{plante} pour aller vers un code
\emph{spécifié}. Le diagnostic de la question 1 vaut autant que la correction :
comprendre pourquoi une récursion ne termine pas est plus formateur que
d'écrire la version juste du premier coup.

La postcondition modulo $9$ introduit l'idée d'une propriété vérifiable en
masse — un invariant mathématique qui sert de test — sans exiger sa
démonstration.
